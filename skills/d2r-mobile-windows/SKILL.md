# D2R Mobile Windows 安装与更新

以用户选择的版本、签名方式和数据保留要求为目标。先判断是首次安装、覆盖更新，还是删除应用后的恢复。具体步骤见 [Windows 流程](references/windows-workflow.md)，只读取当前阶段需要的部分。

## 先收集最少必要信息

- 手机型号、iOS 版本、USB 是否连接并解锁；电脑能否通过苹果通信服务识别。
- 用户自己的游戏文件、已准备资源、已有 IPA 或构建输入的本地路径。只需要密钥文件路径，不读取或输出密钥内容。
- 上次安装的最终 bundle ID、版本、签名账号是否继续使用，以及最新存档是否已保存退出。
- 用户希望正式版还是主分支。查询上游后将版本解析成完整提交 SHA，不把本次参考版本当作永远最新。

可以从现有本地记录和只读设备查询推断信息，避免重复询问。账号密码、双重认证码、设备锁屏密码由用户在对应本机界面输入，不通过聊天、自动填入或日志读取。

## 关键决策

1. **Windows 安装和云端编译分开。** Windows 可用 Sideloadly 签名安装 IPA；原生 iOS 编译需要 macOS/Xcode 或经过检查的云端 macOS 工作流。构建输入 ZIP 不是可安装 IPA。
2. **更新前取得可验证备份。** 备份应用的存档目录，记录相对路径、大小和 SHA-256。更新保持同一签名账号与最终 bundle ID，并覆盖安装。无法取得备份时查明原因再决定；不通过卸载来排错。
3. **已删除应用不等于普通更新。** 明确说明只能恢复现有备份的进度；先检查备份，再恢复到新装应用。不能声称旧手机目录仍然存在。
4. **资源与源码必须匹配。** 依据当前构建报告、资源版本和设备要求核对；旧资源可以复用的前提是兼容验证通过。A14–A16 的 Legacy 需求以当前上游说明为准。
5. **连接错误按层处理。** USB 设备描述符失败属于枚举层；Windows 能显示 iPhone 仍不代表应用通信成功。应用查询、备份和安装服务均需实际成功。
6. **自动续签要检查新版缓存。** 安装勾选续签不等于完成：核对后台、自启动、目标应用续签记录和缓存版本。USB 与 Wi-Fi 分别验收；不默认无线成功。

## 执行与停止条件

- 使用用户自己有权使用的游戏材料。本 Skill 不携带或分发游戏资源、密钥和安装包。
- 只访问选定的 D2R 应用及本次材料。多台手机时先明确目标，避免默认第一台设备。
- 将设备标识、账号信息、存档路径和诊断记录保存在本地；分享仓库只放通用说明与脚本。
- 先运行适用的本地检查并记录被测 SHA、结果及缺少的环境；重要构建保留工作流原有编译、摘要、兼容和产物检查。不要用重复云端重跑代替本地排错。
- 检查工作流执行内容、权限、来源和发布目标。用户自己的游戏产物保存在本地或其授权的私有位置；公开分享 Skill 不代表授权公开游戏制品。
- USB 不稳定、存档备份失败、包摘要不符、签名账号或 bundle ID 不符、资源不兼容时，停止安装相关动作，保留已有材料并说明具体阻碍。不要循环修复驱动或清除配对。
- 根据会话已有授权完成安装和数据恢复；遇到登录、UAC、锁屏、信任或开发者模式等必须本人完成的界面，给出准确步骤后等待，继续不依赖它的工作。

## 验收

按当前任务检查相关项目，并分别报告成功与待确认项：

- 上游完整 SHA、IPA 的 SHA-256、安装后的最终 bundle ID、版本及构建号。
- 备份文件在安装前校验，更新或恢复后逐个核对远端存档摘要；应在首次进入游戏前完成，避免正常游戏写入造成差异。
- 资源源文件校验、传输字节数和最终远端大小；大资源没做全量读回时明确说明只核对了远端大小。
- Sideloadly 续签后台运行、启动项存在、目标应用自动刷新开启、缓存已切换成新版。
- 用户实际能打开游戏、看到预期角色并进入游戏。有提示先完成信任和开发者模式，不能把“安装 Done”当作游戏运行成功。

本地存档清单可用 `python scripts/verify_backup.py <backup-manifest.json>` 校验。该脚本仅校验本地文件，不连接手机或创建备份。清单格式和调用方法见 [Windows 流程](references/windows-workflow.md#本地备份清单)。

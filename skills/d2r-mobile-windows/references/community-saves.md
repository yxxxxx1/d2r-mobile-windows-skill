# 可选社区角色包

仅在用户要求导入成品角色时使用。安装 Skill、覆盖更新和自动续签不自动导入。遵循用户已选的角色或数量；未选择时先列出角色供其选择，不默认写入全部 24 个。

## 兼容范围与实际验证

这些文件已转换为存档格式 **105 / ReignOfTheWarlock**。2026-10-27 本地检查包括文件头、记录长度、独立校验和、SHA-256、完整解析和稳定的读写往返；等级、属性、技能、任务、传送点和物品内容的转换前后比较一致。

设备传输曾在 D2R Mobile **2.0.0 / build 2.1**（源码 `195ae11dc70f1ba7735c6063e1ed81102e1dbf52`）完成：24 个新文件读回摘要一致、导入前已有存档摘要不变。**尚未逐一确认 24 个角色都能在手机进局。** 文件校验和设备传输成功不等于全部游戏兼容性通过，也不代表后续应用或游戏版本自动兼容。

使用前查询目标应用版本和用户已有 `.d2s` 的实际格式。不要只修改文件头版本号、盲目降级，或为符合本包而更换用户游戏资源。

## 先验证本地材料

1. 对 ZIP 计算 SHA-256，须与上面的值一致。Windows 可用 `Get-FileHash -LiteralPath <ZIP路径> -Algorithm SHA256`。
2. 检查 ZIP CRC、条目名及清单，确认没有绝对路径、目录穿越或重复条目，再解压到新的本地准备目录，不直接解压到手机或备份目录。
3. 用 Skill 的只读校验器验证解压后的全部文件：

   ```sh
   python scripts/verify_backup.py <解压目录>/backup-manifest.json
   ```

   应得到 `save_files: 24`、`save_bytes: 56784`。包里的 `prepared_not_imported`、`device_imported: false` 表示分发材料未对应本次设备操作，不是读取用户手机状态。
4. 根据用户选定角色，只准备对应目录；若生成子集清单，只保留选中角色的 `saves` 记录，并再次调用只读校验器。

## 备份后追加导入

沿用 [Windows 流程](windows-workflow.md) 的设备选择和备份方法；密码、信任和解锁由用户本人完成。

1. 用户在游戏中保存退出，手机连接并解锁；核对目标手机及已安装应用的实际 bundle ID。
2. 完整备份当前 `/Documents/save`，记录路径、字节数及 SHA-256，先校验本地备份，再确认手机存档没有在备份后发生变化。使用当天最新进度，不直接复用历史备份。
3. 列出目标存档目录，按大小写不敏感比较检查重名。发现同名角色时停止该角色的写入，保留已有文件；不要直接覆盖，也不要只改文件名冒充新角色。
4. 在游戏 `save` 目录外建立本次专用暂存目录，上传所选角色并读回验证 SHA-256，然后逐个将其目录移动至 `/Documents/save/<角色名>`。移动前再次检查目标不存在。
5. 读回全部新增文件，逐个核对摘要；与备份逐一比较原有文件的大小与摘要，并核对资源文件状态。不要更改共享仓库、应用安装和续签配置。
6. 部分失败时记录哪些角色已经成功，不把整批重跑当作覆盖授权。保留本地来源、备份和本次结果，先查明失败再继续。
7. 用户打开游戏，确认角色出现并尝试进局。如新增后黑屏，先查该次启动日志；必要时将本次新增角色可逆地移到 `save` 以外隔离排查，不删除原角色或卸载应用。

## 后续更新与已经导入过的角色

更新应用前重新备份手机当前全部存档，包括这些角色新增的地图、控制配置、进度与物品。随附 ZIP 是初始成品模板，不能用于“刷新”已玩过的角色；否则会丢失用户后续进度。正常覆盖更新保留同一签名账号和最终 bundle ID，并继续核对自动续签缓存。

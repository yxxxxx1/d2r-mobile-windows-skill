# Windows 实施流程

## 信息来源与版本

先查当前的 [d2r-mobile](https://github.com/jhaizhou-ops/d2r-mobile) 和 Releases；需要云端构建时查 [d2r-mobile-build](https://github.com/jiayx/d2r-mobile-build) 当时的 README 与工作流，不直接套用旧输入。Sideloadly 从 [官方网站](https://sideloadly.io/) 获取。记录核对日期及完整 SHA。

参考实测：2026-10-26，iPhone 13 Pro Max / A15 / iOS 26.6.2，源码 `195ae11dc70f1ba7735c6063e1ed81102e1dbf52`，应用 `2.0.0 / build 2.1`。这不是对后续版本的固定要求。

## 1. USB 与苹果组件

1. 手机保存退出游戏、USB 连接、解锁，按需确认信任电脑。
2. 查看当前 Windows PnP 设备、Apple Mobile Device Service 及应用通信结果。不能只用充电状态判断连接。
3. 如果出现“设备描述符请求失败／错误 43”，先更换直连接口或可传数据的线，并重启手机后重连；不要先更改游戏数据。
4. PnP 正常但通信工具查不到手机时，检查苹果通信服务、驱动来源和冲突的组件版本。修复应使用签名有效、来源明确的苹果支持安装程序。需要管理员权限时由用户确认 UAC。
5. 修复组件时可暂时关闭 Sideloadly 及其后台，完成后重新启动并保留配置。已有 Store 版 Apple Devices 提示移除旧支持组件时，先评估兼容性，不能顺手移除另一套正在使用的组件。

本次故障的恢复顺序是：修复 Apple Mobile Device Support → 关闭占用程序让修复完成 → 重启并重新连接手机 → PnP 与设备通信均成功。它是已验证案例，不是所有 USB 故障都必须执行的固定动作。

一轮有证据的修复和物理重连仍失败时，保留日志、明确当前失败层级，再请求有针对性的用户操作；不反复卸载驱动。

## 2. 查询、备份与清单

可使用隔离 Python 环境中的 `pymobiledevice3`。API 随版本变化，先检查安装版本和实际签名。实测环境是异步 API：

- `await create_using_usbmux(connection_type='USB')`，进入上下文后核对目标 UDID；多设备需按所用版本的选设备参数明确指定。
- `InstallationProxyService` 的 `get_apps(application_type='User', bundle_identifiers=[bundle])` 获取版本及应用标识。
- `await HouseArrestService.create(ld, bundle, documents_only=True)` 访问应用文件。
- 实测文档目录是 **`/Documents`**，存档是 `/Documents/save`；`documents_only=True` 不表示可以把 `/` 当作文档根。

仅处理目标 D2R 应用，不输出全部应用清单。记录原签名后的最终 bundle ID，而不是只看未签名 IPA 的标识。

备份应先完成枚举和下载，再写完成清单。逐文件记录字节数、SHA-256；目录遍历必须限制在选定存档目录下。失败或中断的文件夹不算完整备份。应用不存在时核实是否删除、卸载但保留数据、使用其他容器或标识改变，不直接推断存档还在。

### 本地备份清单

清单位于备份根目录，文件存放在它旁边的 `save` 下。以下摘要是格式示意，实际备份必须记录真实值：

```json
{
  "bundle_id": "应用实际签名后的标识",
  "saves": [
    {"path": "save/角色/角色.d2s", "bytes": 1234, "sha256": "文件实际的64位十六进制SHA256"}
  ]
}
```

调用 Skill 中的脚本：

```sh
python scripts/verify_backup.py /path/to/backup-manifest.json
```

脚本只读校验 `saves` 中的文件，拒绝空清单、重复路径、目录外路径、大小或摘要不符。清单中的 `resources` 等其他字段不会被该脚本校验；资源需要单独核对。

如果用户已经删除游戏，只能恢复仍持有的备份。说明备份日期和可恢复范围，校验本地文件后，再把它恢复到重新安装的应用；不承诺找回未备份的新进度。

## 3. 准备 IPA

- 已有匹配 IPA：核对其来源、预期摘要、ZIP CRC、Info.plist 的最低系统、版本和标识，确认设备可用。
- 只有源码或构建输入：Windows 不进行原生 Xcode 编译；可在用户授权的私有仓库使用经过检查的云端 macOS 工作流，或其可用的 Mac。
- 使用完整源码 SHA；工作流实际引用的工具 SHA、输入摘要与构建报告也需记录。解析主分支后不能在构建过程中悄悄换目标。
- 本地先跑适用的项目测试。Windows 无法跑的 Xcode 构建、生成资源检查或实机测试要单独注明，交由相应环境验证，不能当作通过。
- 保留工作流完整的兼容性、原生编译、产物摘要及发布检查。所有相关任务成功后再安装。
- 比较构建报告中的游戏程序、资源清单和 Legacy 摘要，决定原资源能否复用。资源版本不兼容时先解决，不装一个已知缺材料的包。

本次参考流程用 `Build IPA` 的 `source_repository`、`source_ref` 和 `prepared_input` 输入。后续字段与格式以当时工作流为准。构建材料应来自用户有权处理的文件；本 Skill 不提供公共游戏材料地址。

## 4. Sideloadly 安装

1. 选择已确认的目标手机及通过校验的 IPA，保持原签名账号和最终应用标识。
2. 根据用户需求开启自动续签。识别当前版本实际 UI 标签／工具提示，不能把历史屏幕坐标或旁边的隐藏信息按钮当作通用控件。
3. 使用当前可用的 UI 工具或让用户操作。不要假设 AI 环境支持原生窗口控制；没有相关能力时明确指导用户完成这一段。
4. 登录密码、双重认证由本人输入；有缓存时可正常复用既有会话，不读取认证数据库字段。
5. 安装到 `Done / 100%` 后，用设备服务读取最终 bundle ID、版本和构建号。

普通更新使用覆盖安装；不卸载游戏、不切换标识或签名账号。下载一个新包不会自动更新 Sideloadly 的续签缓存，安装后还需核对。

## 5. 数据恢复与资源传输

首次安装或删除后的重装，需要导入资源；兼容的覆盖更新通常只核对，无需重传。

手机目录结构以当前版本为准，本次实测是：

```text
Documents/
├── save/
├── D2R Mobile Resources/
│   └── data/
│       ├── build_manifest.psv
│       └── *.data
└── Legacy Device Pack/
    ├── manifest.json
    └── data/*.data
```

核对解压后大小及安装临时空间。先验证本地源文件摘要，按文件分块传入暂存文件，例如 `.codex-uploading`，关闭句柄、核对长度后改为正式文件名。中断时保留本地源文件和完成记录，恢复前核对已存在的目标文件。

存档恢复先校验备份，再写目标并核对远端 SHA-256。已有不同内容的存档先另存、评估和处理，不直接覆盖。资源通常核对源摘要、传输字节数和最终远端大小；没有逐字节读回整套大资源时不声称做了远端哈希校验。

将手机上的 `boot.txt` 等目标应用日志作为诊断材料；不扩大到无关应用数据。

## 6. 信任与开发者模式

- 未受信任：设置 → 通用 → VPN 与设备管理 → 对应的开发者 App／签名账号 → 信任，手机联网完成验证。可参考 [Apple 信任说明](https://support.apple.com/zh-cn/118254)，个人开发签名与企业签名的具体标签可能不同。
- 需要开发者模式：设置 → 隐私与安全性 → 开发者模式 → 开启并重启 → 解锁后在弹窗再次确认开启。见 [Apple Developer Mode](https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device)。

这些由用户在手机上完成；不通过删除游戏解决。

## 7. 自动续签与最终验收

确认后台进程和用户登录启动项，保持电脑运行且能检测手机。免费签名有效期和限制以 Apple／Sideloadly 当时说明为准。

如果当前 Sideloadly 仍使用 SQLite 记录，可只读核对该应用的最终 bundle ID、刷新状态、最近更新时间、错误和关联缓存大小／摘要。实测版本 `one_off=0` 代表启用续签，但不能未经核对就套用于未来数据库结构。不要直接改数据库或读取 Apple ID、密码、token 等认证字段。

续签缓存须指向新 IPA，避免过几天刷回旧版本。USB 已成功不代表 Wi-Fi 已成功；无线连接作为用户需要时的独立验证。自动续签不负责自动追踪 GitHub 更新。

在用户首次进入游戏前，核对存档摘要与资源文件；然后由用户确认角色和进局。报告实际验证的范围，保留本地安装与备份记录供下次更新。
